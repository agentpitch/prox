# Аудит кода pitchProx — 2026-07-28

Исходная точка: commit `7d80802abe9b`.

Цели аудита:

- минимальное потребление RAM и CPU в простое;
- отсутствие неограниченного накопления памяти, файловых данных, записей о завершённых процессах и сетевых потоках;
- устойчивость при многодневной работе, ошибках диска и повреждённой истории;
- сохранение работающего персонального WebUI без добавления аутентификации;
- проверяемые и откатываемые изменения конфигурации.

## Исправленные недостатки

### 1. Неограниченный рост очередей истории при ошибке диска

Раньше неудачная запись могла оставлять новые записи в растущих массивах и картах без жёсткого предела. При заполненном или недоступном диске это создавало риск постоянного роста RAM.

Исправлено:

- аварийные очереди логов, соединений, заблокированных соединений, трафика и статистики правил имеют жёсткие верхние границы;
- переполнение отбрасывается и учитывается счётчиком `discarded_pending`;
- после ошибки повтор выполняется не чаще одного раза в 30 секунд;
- штатный сброс остаётся пакетным: через 3 секунды либо при достижении небольшого порога очереди.

### 2. Потеря или дублирование истории при частичной ошибке записи

Пакет мог быть удалён из RAM до подтверждённой записи всех файлов.

Исправлено:

- пакет сначала отделяется от активной очереди;
- успешно записанные категории помечаются как завершённые;
- незаписанные данные возвращаются в ограниченную очередь;
- при ошибке внутри многофайловой операции затронутые файлы откатываются к исходному размеру;
- незавершённый JSONL-хвост после аварийного завершения обрезается при следующем запуске;
- отдельные повреждённые завершённые строки пропускаются, не скрывая соседние валидные записи.

`fsync` после каждого пакета намеренно не добавлен: история является диагностической, а постоянная синхронизация заметно увеличила бы дисковую активность и энергопотребление.

### 3. Чтение больших журналов целиком в RAM

Страница заблокированных соединений, удаление записей и ограничение размера файла могли материализовать слишком большой объём данных.

Исправлено:

- пагинация читает JSONL с конца и хранит только требуемую страницу;
- удаление записей выполняется потоковой перезаписью;
- ограничение размера копирует только допустимый хвост файла;
- размер одной строки ограничен, чрезмерно длинная повреждённая строка отбрасывается.

### 4. Повторное использование PID

Путь процесса кэшировался только по PID. После завершения процесса Windows может выдать тот же PID другому приложению.

Исправлено:

- идентичность кэша теперь состоит из PID и времени создания процесса;
- путь повторно используется только после проверки времени создания;
- завершённые и просроченные записи удаляются при очередном востребованном обновлении;
- таблицы IPv4 и IPv6 обновляются независимо: временная ошибка одной семьи не уничтожает корректный кэш другой.

### 5. Удержание разросшихся map после сетевой нагрузки

Удаление элементов из Go `map` не обязано возвращать память её внутреннего массива.

Исправлено:

- `FlowTable`, таблица активных relay-соединений и таблица HTTP-соединений отслеживают пик;
- после полного опустошения таблица с пиком от 64 элементов заменяется новой маленькой `map`;
- маленькие таблицы не пересоздаются на каждом соединении, чтобы не увеличивать число аллокаций.

### 6. Фоновая работа при отсутствии потоков

Очистка flow table раньше просыпалась по постоянному ticker.

Исправлено:

- timer очистки запускается только после регистрации потока;
- после удаления последнего потока timer останавливается;
- общий WinDivert redirector закрывается сразу после опустошения flow table;
- история также перешла с постоянного ticker на таймер, существующий только при наличии работы.

### 7. Игнорирование ошибок WinDivert

Результаты `Send` и `CalcChecksums` частично игнорировались, что могло приводить к тихой потере пакетов и зависшим flow-записям.

Исправлено:

- проверяются ошибка и короткая запись;
- при ошибке начального перенаправления flow удаляется, а исходный SYN по возможности отправляется без изменения;
- сообщения об ошибках ограничены по частоте, чтобы повторяющаяся проблема не создала логовый шторм.

### 8. Неполный IPv6 и TLS разбор

IPv6 TCP распознавался только без extension headers, а TLS SNI — только если весь ClientHello находился в одной TLS record.

Исправлено:

- добавлен ограниченный проход не более чем по восьми IPv6 extension headers;
- не-первые фрагменты и усечённые заголовки отбрасываются;
- ClientHello собирается не более чем из восьми TLS records и в пределах настроенного `sniff_bytes`;
- имя хоста проходит проверку длины, меток и допустимых символов.

### 9. Неатомарное применение конфигурации

Конфигурация могла быть записана и опубликована до проверки, что новые listener/interception параметры действительно запускаются.

Исправлено:

- изменения, требующие перезапуска маршрутизации, сначала активируются;
- при неудаче восстанавливается предыдущая конфигурация и предыдущий runtime запускается снова;
- только успешно активированная конфигурация сохраняется;
- внутренняя копия `config.Store` меняется только после успешной замены файла.

### 10. Неограниченные HTTP-заголовки и соединения

Локальный HTTP-сервер не имел явной границы числа одновременных соединений, а `ReadString` мог наращивать буфер для длинной строки.

Исправлено:

- не более 64 одновременных соединений;
- не более 100 заголовков и 32 KiB суммарного размера;
- чрезмерно длинная отдельная строка отклоняется без наращивания буфера;
- после высокого пика пустая таблица соединений освобождает backing storage;
- адрес WebUI должен быть IPv4/IPv6 loopback или `localhost`.

Аутентификация не добавлена: WebUI остаётся персональным локальным интерфейсом, как и требовалось.

### 11. Лишняя периодическая нагрузка

Исправлено:

- принудительное освобождение heap выполняется раз в 5 минут только при заметном объёме освобождаемой памяти или крупной куче;
- активное сканирование TCP для открытого WebUI замедлено с 7 до 10 секунд;
- тяжёлый snapshot WebUI запрашивается раз в 15 вместо 7 секунд;
- резервная копия `app.js.bak`, ошибочно попадавшая в embedded assets, удалена.

### 12. Несоответствие репозитория и документации

Исправлено:

- module path изменён с `github.com/openai/pitchprox` на `github.com/agentpitch/prox`;
- описание несуществующих per-flow WinDivert handles заменено на фактическую схему с ленивым общим redirector;
- архитектурная документация дополнена правилами жизненного цикла ресурсов.

## Архитектурные решения

### JSONL вместо SQLite/WAL

SQLite/WAL не добавлен. В текущем процессе один пакетный writer, а запросы ограничены коротким retention window и часовыми сегментами. WAL добавил бы библиотеку БД, страницы кэша и checkpoint-работу без подтверждённой необходимости в конкурентных писателях. После исправления потоковых запросов, восстановления хвоста и ограниченных очередей JSONL лучше соответствует цели минимальных RAM и CPU.

### Общий redirector вместо per-flow handles

Сохранён существующий общий redirector:

- он создаётся только при первом реально перехватываемом потоке;
- закрывается после последнего потока;
- в абсолютном простое остаётся только дешёвый SYN-классификатор.

Сравнение общего и per-flow вариантов на реальном WinDivert не выполнялось, потому что на компьютере уже работает основной экземпляр pitchProx. Корректный A/B-тест требует отдельной VM или отдельного тестового окна без основного драйверного трафика; иначе измерение будет искажено и может нарушить работу основного приложения.

## Проверки

Успешно выполнены:

- `go test -count=5 ./...`;
- `go vet ./...`;
- `node --check internal/webui/dist/app.js`;
- пятикратный тест двух последовательных серий по 1000 HTTP-соединений;
- тест восстановления незавершённого JSONL-хвоста и пропуска повреждённой строки;
- тест жёстких пределов аварийных очередей истории;
- тест высокого пика и полного освобождения flow table;
- тест отката runtime после ошибки нового listener;
- тест IPv6 extension headers и TLS ClientHello из нескольких records;
- release-сборка с `-trimpath -ldflags="-H=windowsgui -s -w"`.

Микробенчмарк flow table на тестовой машине:

- неизвестный пакет: `32.41 ns/op`, `0 B/op`, `0 allocs/op`;
- известный пакет: `38.15 ns/op`, `0 B/op`, `0 allocs/op`;
- register/delete: `176.0 ns/op`, `144 B/op`, `1 alloc/op`.

## Что ещё нужно проверить отдельно

- elevated end-to-end запуск с WinDivert и реальным трафиком;
- 48–72-часовой soak test с контролем working set, private bytes, handles, goroutines, flow count и history queues;
- A/B shared/per-flow redirector в изолированной VM;
- Windows Service и tray через реальный SCM/Explorer.

Эти проверки намеренно не запускались рядом с уже работающим основным pitchProx. Race detector также недоступен в текущем toolchain (`CGO_ENABLED=0`, C-компилятор отсутствует); вместо него выполнены повторные тесты и `go vet`.
