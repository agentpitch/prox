# Ревизия фонового потребления ресурсов — 2026-09-23

Исходная версия: `89e6b624ab52ef952a97605733a6c10f34c94518` (v0.43).
Проверены маршрутизация, Windows owner lookup, перехват, relay, история,
мониторинг, HTTP/SSE, WebUI, трей, обновление и завершение приложения.
Три независимых направления ревизии дополнены перекрёстным просмотром изменений.

## Исправленные причины нагрузки и удержания ресурсов

1. **Определение HTTP hostname.** Уже полученный заголовок повторно разбирался
   после каждого байта; `Split` и преобразование всех строк создавали большой
   объём временных данных. Теперь разбираются все доступные байты, строки
   обходятся без массива копий и без обработки тела как заголовков.
2. **Таблицы потоков и активных соединений.** Полная пересборка после каждых
   64/256 удалений была дорогой при тысячах остающихся соединений. Пересборка
   теперь требует пропорционального числу живых записей количества удалений;
   освобождение памяти при опустошении и значительном сокращении сохранено.
3. **Долгоживущие соединения.** Буферы sniff и HTTP CONNECT освобождаются после
   передачи накопленного префикса, вместо удержания до закрытия туннеля.
4. **Остановка proxy.** Запоздало зарегистрированные входящие и исходящие
   сокеты закрываются, если очистка уже началась. Отмена контекста прерывает
   HTTP/SOCKS handshake; обработчик отмены отсоединяется либо ожидается перед
   передачей успешного соединения вызывающему коду.
5. **Ответ CONNECT.** Суммарный размер заголовков ограничен 64 КиБ, включая
   случай одной строки без перевода строки. Это устраняет неограниченный рост
   памяти при некорректном ответе прокси.
6. **История блокировок.** Переполнение больше не вызывает копирование почти
   всего файла при каждой следующей записи. После сжатия оставляется 12,5%
   свободного места; жёсткий лимит сохранён. Поэтому фактически сохранённый
   объём колеблется примерно между 87,5% и 100% лимита. Крупная последняя запись,
   помещающаяся в жёсткий лимит, сохраняется.
7. **Телеметрия без UI.** SSE JSON не сериализуется без подписчиков. Запись
   предупреждений в историю продолжается. После `Store.Close` новые записи
   больше не попадают в очереди, для которых уже нет фонового обработчика.
8. **HTTP/SSE.** Заблокированные записи имеют deadline; ответ при перегрузке
   не задерживает accept loop надолго. Регистрация соединения и WaitGroup
   синхронизированы с завершением. Отключение EventSource сразу освобождает
   подписку вместо ожидания следующего 25-секундного heartbeat; дополнительный
   читатель закрывается и ожидается при каждом выходе.
9. **Трей.** Динамические иконки создаются из DIB в памяти, без временного файла
   и повторной загрузки с диска. Остановка ожидает poller; владение HICON
   синхронизировано. Исправлено освобождение окна и mutex повторного экземпляра.
10. **Скрытая вкладка.** Опрос обновления в Settings также останавливается при
    скрытии и BFCache. При возвращении состояние восстанавливается; закрытие
    диалога удаляет обработчики. Проверка релизов отменяется и ожидается при
    закрытии backend updater.
11. **Фоновый GC.** Сам по себе большой живой heap больше не вызывает полную
    сборку мусора и сброс рабочего набора каждые пять минут. Решение принимается
    по свободным страницам, которые ещё не возвращены ОС.
12. **Правила и Windows.** Путь приложения и hostname нормализуются лениво
    один раз на решение. Неизменившийся кэш процессов не копируется. Пустые и
    усечённые TCP-таблицы проверяются до обращения к данным и выделения памяти.
    Повторные поиски владельца SYN обновляют снимок с ограниченным backoff и
    поддержкой отмены вместо повторного чтения неизменного снимка.

## Измерения отдельных операций

Windows/amd64, Ryzen AI 9 HX 370, Go **1.26.5**. До и после использовались
одинаковые benchmark, версии компилятора и оборудование. Для sniff и FlowTable
приведены медианы трёх запусков. Это микротесты, а не проценты ускорения всего
приложения; результаты зависят от правил и фактического трафика.

| Сценарий | До | После | Выделено байт на операцию, до → после |
|---|---:|---:|---:|
| HTTP sniff, готовый заголовок около 3 КиБ | 5,995 мс | 0,916 мкс | 10 008 728 → 4 176 |
| FlowTable: открытие/закрытие при 4096 постоянных потоках | 11,023 мкс | 0,133 мкс | около 15 500 → 144 |
| Monitor: смена соединения при 4096 активных | 2,575 мкс | 0,514 мкс | 5 747 → 629 |
| Запись в заполненный dropped log около 1 МиБ | 8,870 мс | 0,485 мс | 166 993 → 6 237 |
| Событие без SSE-подписчиков | 3,432 мкс | 0,022 мкс | 5 431 → 16 |
| Preflight: 256 правил, требуется hostname | около 21 мкс | около 3,5 мкс | около 6 148 → 24 |

У правил число аллокаций сократилось с 256 до одной. Быстрый окончательный
Direct-путь по-прежнему не выделяет память; его микротест не показал ускорения.
У HTTP sniff число аллокаций сократилось с 12 143 до четырёх.

## Проверки и границы выводов

- `go test -mod=readonly -count=1 -cover ./...` и `go vet -mod=readonly ./...`
  прошли с Go 1.26.5; итоговый `go test -mod=readonly -race -count=1 ./...`
  также прошёл (Windows, GCC 14.1.0).
- Синтаксические проверки JS и все 35 Node-тестов прошли с Node 24.19.0.
  Release pipeline дополнен lifecycle-тестами; он по-прежнему использует
  закреплённый Node 22.17.0. Локальная сборка для проверки не является
  опубликованным релизным пакетом.
- Проверены 500 нативных циклов создания/удаления иконок; USER resources
  1 → 2, без роста по числу циклов. SSE прошёл по 50 циклов закрытия клиентом
  и выключения сервером с нулём оставшихся подписчиков.
- Исходный и исправленный EXE запускались отдельно, без повышения прав,
  WinDivert и трея, с Direct-правилами и разными конфигурациями/портами.
  После прогрева за 30 секунд у обоих CPU time не увеличился в разрешении
  счётчика Windows. Working set составлял около 13 МиБ, private bytes около
  48 МиБ; роста памяти и дескрипторов за этот короткий интервал не было.
  Оба экземпляра штатно завершились с кодом 0.
- Действующий пользовательский процесс не перезапускался и не заменялся.
  Отдельная 30-секундная выборка показала стабильные private bytes около
  83,8 МиБ и 1037–1039 handles. Нагрузка этого процесса не контролировалась,
  поэтому это наблюдение не используется как сравнение производительности.
- Суточный/недельный soak-тест с реальными Proxy/Chain-правилами, WinDivert,
  установленной SCM-службой и обновлением исполняемого файла не проводился.
  Нельзя на основании микротестов обещать конкретный процент снижения среднего
  CPU/RAM или отсутствие всех возможных утечек. Для дальнейшего измерения
  уже есть ресурсная диагностика приложения и `tools/analyze_resource_log.ps1`.
